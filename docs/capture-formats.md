# 擷取與錄影的可行格式

決定（2026-09-01）：**錄影做完整功能**，不是只做截圖，也不是只做無聲 GIF。這份文件
記錄在「全 binary 禁 cgo」之下，這句話實際能做到什麼、要付什麼代價。

## 問題的形狀

錄影檔要三樣東西：容器、視訊編碼、音訊編碼。純 Go 目前的供給不平均。

| 層 | 純 Go 供給 | 說明 |
|---|---|---|
| 容器 | 有 | `github.com/abema/go-mp4` 做 MP4 box 層的讀寫。AVI 更簡單，自己寫約兩百行。 |
| 視訊 | 只有 MJPEG | `image/jpeg` 在標準函式庫裡。H.264 沒有成熟的純 Go 編碼器。 |
| 音訊 | 只有 PCM | AAC、MP3、Opus 都沒有成熟的純 Go 編碼器。 |

`go-mp4` 是容器層工具，本身不編碼；官方說明寫的是「提供 MP4 的低階 I/O 介面」，
不適合做複雜資料轉換。所以它解決的是「怎麼把已編碼的取樣包成 .mp4」，不是
「怎麼把 framebuffer 變成 H.264」。

H.264 的 Go 生態幾乎都是 C 綁定：`gen2brain/x264-go`、`sergystepanov/x264-go`、
`cloud-game` 的 `h264` 套件都走 cgo。唯一避開 cgo 的是 `y9o/go-openh264`，它用
purego 在執行期載入 Cisco 的 OpenH264 共享程式庫——建置期沒有 C 編譯器，執行期
仍需要那個 `.so`／`.dylib`。

## 三個候選

### 甲：MP4／MJPEG＋PCM（純 Go，無執行期相依）

`go-mp4` 寫容器，`image/jpeg` 逐幀編碼，音訊以 PCM 取樣寫入。

- 建置與執行都不需要任何 C 的東西，跨三個平台行為一致。
- VLC、mpv、QuickTime 可播；瀏覽器與部分手機播放器不吃 MJPEG。
- 位元率估算：320×240、品質 80 的 JPEG 約每幀 10–15 KB，60 fps 約 0.6–0.9 MB/s，
  一分鐘約 40–55 MB。音訊 PCM 48 kHz 立體聲另加 0.19 MB/s。

### 乙：MP4／H.264＋AAC（要執行期載入原生函式庫）

以 `go-openh264` 走 purego 載入 OpenH264。Go binary 本身仍無 cgo。

- 檔案小、到處都能播，等同 Bcan 的輸出。
- 代價：發行包要處理 OpenH264 的取得與授權。Cisco 的免權利金條款綁在「由 Cisco
  發布的二進位檔」上，自行重新散布會落在條款外，通常要在首次使用時下載。
- 音訊仍缺 AAC 編碼器，得退回 PCM 或另尋方案；這一項尚未查到純 Go 的解。
- 新增一種失敗模式：函式庫不存在或版本不符時錄影不可用，介面要能說清楚。

### 丙：甲為預設，乙為選配

預設輸出甲，另開一個設定讓使用者指向本機的 OpenH264。介面上是同一個「開始錄影」。

## 與硬體證據的關係

錄影與截圖都從 UM6618 的顯示孔徑取像，不套視訊濾鏡、不含疊加層。錄影本身不得影響
排程：編碼在模擬迴圈之外進行，來不及時丟棄的是**編碼工作**而不是模擬幀，且要記錄
丟棄數量。開著錄影的工作階段，其 frame 雜湊仍應與未錄影時相同——這是驗收條件。

## 實作結果（2026-09-01）

實作的是 **AVI 容器 + MJPEG 視訊 + PCM 音訊**，不是 MP4，理由有兩個，兩個都與
「甲：純 Go、無執行期相依」這個決定一致：

1. `abema/go-mp4` 是容器層工具，MJPEG 進 MP4 還是要自己組 `stsd`／`stts`／`stsc`／
   `stsz`／`stco` 取樣表，而 MJPEG 在 MP4 裡的播放器支援明顯比在 AVI 裡差。
2. Bcan 自己的第二種錄影格式就是 AVI/MJPEG，對齊它不需要解釋。

換句話說，改的是容器不是編碼；決定裡「純 Go、無執行期相依、MJPEG＋PCM」三件事
都成立。要 `.mp4` 副檔名的話，`go-mp4` 這條路仍然開著，那是另一輪工作。

實作在 `capture` 套件。三件值得記的事：

- **標頭的回填位移在寫入時記下來，不是手算的常數。** 第一版用手算位移，音訊的
  `dwLength` 與 `movi` 的大小都指錯位置；檔案看起來還是「有東西」，要到播放器
  拒絕才會發現，而那時候離出錯的地方已經很遠。
- **收尾是必要的，不是可選的。** RIFF 的大小欄位、`dwTotalFrames`、兩條串流的
  `dwLength` 全部在 `Close` 才回填。第一次真機錄影忘了在結束前收尾，得到一個
  1.5 MB、資料完整、但標頭全是 0 的檔案——播放器一幀也讀不出來。入口現在 defer
  `Session.Shutdown()`。
- **錄影來源是顯示孔徑，不含覆蓋層也不套濾鏡**，所以錄下來的畫面與截圖是同一個
  東西；`TestCaptureDoesNotChangeTiming` 確認開著錄影跑，指令數與 framebuffer
  雜湊都不變。

外部接收端（`--capture-sink`）把原始 320×240 RGBA 幀寫給一個外部程序，讓想要
H.264 小檔案的使用者自備 ffmpeg。內建那條路不需要任何外部工具。
