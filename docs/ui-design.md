## 1. 定案約束

這一節列的是設計的輸入條件，不是本文的主張。

| 編號 | 約束 | 來源 |
|---|---|---|
| C1 | 發行平台只有 Linux 桌面、macOS、Android。Windows 與瀏覽器不在範圍 | 專案定案 |
| C2 | Android 是觸控裝置，無實體鍵盤，直式與橫式都要能用 | 專案定案 |
| C3 | 不得使用任何系統原生 widget（GTK／Qt／Cocoa／Android View）繪製介面 | 專案定案 |
| C4 | 介面自繪：純 Go 的 `ui` 套件把畫面畫進 RGBA 緩衝，前端只貼圖與翻譯輸入 | 專案定案 |
| C5 | UI 不得改寫晶片狀態；暫停只停止呼叫端推進時間線，不動 scheduler 餘數 | `AGENTS.md` |
| C6 | 金手指是 C5 的唯一例外，且只能寫 Work RAM，定位為除錯／作弊工具 | 專案定案 |
| C7 | 發行 binary 禁止 cgo | `CONTEXT.md`，2026-09-01 定案 |
| C8 | repo 與發行包不含 ROM、BIOS 或遊戲畫面 | `AGENTS.md` |
| C9 | 原生解析度 320×240，256 色調色盤；256 模式下 UM6618 顯示孔徑只有 256 欄 | `docs/umc6618-implementation.md` |
| C10 | 九款卡帶的 1200-frame 指令數與 framebuffer SHA-256 不得因 UI 改變 | `docs/verify-rom-matrix.md` |

C1 有一個立即後果要記錄：目前支持「禁 cgo 政策已成立」的建置證據來自
`js/wasm` 與 `windows/amd64` 兩個目標（`docs/ebitengine-frontend.md`）。這兩個目標
退出發行範圍之後，那組證據不再涵蓋任何發行平台，`darwin` 與 `android` 的建置矩陣
必須重跑才算數。詳見 §11 的 G1。

## 2. 平台矩陣與前端邊界

| 目標 | 視窗／輸入 | 音訊 | `CGO_ENABLED=0` 現況 | 缺口 |
|---|---|---|---|---|
| `linux/amd64` 桌面 | `frontend/x11`（`jezek/xgb`，純 Go） | 外部播放程序 | 已建置；八款 ROM 與 headless 完全一致 | 純 Go 音訊、Wayland、全螢幕、手把、視窗縮放 |
| `darwin/arm64`、`darwin/amd64` | Ebitengine（`internal/glfw` 走 purego） | `oto/v3` darwin 路徑未實測 | 未實測 | 建置矩陣、手把、實機 smoke |
| `android/arm64` | Ebitengine mobile（`ebitengine/gomobile`，已在 `go.mod` 作 indirect） | `oto/v3` android 路徑未實測 | 未實測 | gomobile 走 JNI，是否可在 `CGO_ENABLED=0` 成立未知 |

`ui` 套件對這三者一視同仁：它只知道「表面大小、縮放倍率、指標粗細、可用能力集」，
不知道自己被畫在 X11 的 `PutImage`、Ebitengine 的 texture 還是 Android 的 surface 上。

前端能力以查詢介面回報，UI 依回報結果決定顯示或停用項目：

```go
type Capabilities struct {
    Fullscreen   bool // 前端能否切換全螢幕
    WindowResize bool // 視窗可否自由縮放
    Gamepad      bool // 前端是否提供手把事件
    Haptics      bool // 觸覺回饋（Android）
    FilePicker   bool // 是否有系統檔案選擇器可用（Android SAF）
    Filters      []FilterID // 該前端實際能執行的影像濾鏡
    AudioSink    AudioSinkKind // 內建播放器／外部程序／無
}
```

理由：能力差異是平台事實，不是設定。把它當設定會讓使用者在 X11 上打開一個不存在的
全螢幕開關；把它硬編在 UI 裡則會讓 UI 認識平台，違反 C4。

## 3. 架構

```
                    ┌──────────────────────────────┐
   machine core ───►│ UM6618 framebuffer 320×240   │──┐
   （唯讀快照）      └──────────────────────────────┘  │
                                                       ▼
   ui 狀態機 ───────► overlay RGBA（表面原生解析度）──► ui.Compose ──► 前端貼圖
        ▲                                                    │
        │ 抽象事件                                  Intent    │
        └────────────── 前端（X11／Ebitengine／Android）◄──────┘
                                    │
                                    ▼
                              入口（cmd/*）執行 Intent
```

三條邊界：

1. **`ui` 不 import 任何前端套件。** 以 `go list -deps ./ui` 斷言，和 machine core
   不 import Ebitengine 的規則同層級。
2. **`ui` 不持有 `*machine.System`。** 它拿到的是唯讀快照介面與一個 Intent 通道；
   要求動作時回傳意圖，由入口在 frame 邊界執行。這是 C5 在程式結構上的落實：
   UI 沒有寫入 machine 的能力，不是靠自律。
3. **overlay 畫在表面原生解析度，不畫在 320×240。**

第三點是與初版規劃不同的地方，理由：若 UI 畫進 320×240 再與遊戲畫面一起放大，
中文字最多只有 12–13 px 高並被整數倍放大成馬賽克，而觸控目標在 320×240 的座標系
無法表達 44 單位的最小命中區。代價是 overlay 的畫面雜湊會隨表面大小改變，因此
§10 的驗收固定兩組表面尺寸。遊戲 framebuffer 的雜湊不受影響，兩者分開雜湊。

唯讀快照介面：

```go
type Snapshot interface {
    Framebuffer() *image.RGBA          // 借用，不得寫入
    FrameIndex() uint64
    Instructions() (m68k, m65c02 uint64)
    Halt() (HaltReason, bool)          // fail-closed 停機原因
    Cartridge() (title string, sum [32]byte, size int64)
    Firmware() FirmwareIDs             // IPL／key／兩個音效 BIOS 的 SHA-256
    ReadWorkRAM(dst []byte, addr uint32) int
    VideoRegisters() [256]uint16
    LayerMask() uint32
}
```

Intent 清單：

```
LoadCartridge{Path}      UnloadCartridge{}        Reset{Cold|Soft}
SaveState{Slot}          LoadState{Slot}          DeleteState{Slot}
SetPaused{bool}          SetPacing{bool}          SetVolume{0..100}
Capture{Screenshot|ClipStart|ClipStop}
ApplyConfig{Config}      SetLayerMask{uint32}
PokeWorkRAM{Addr,Width,Value}                     Quit{}
```

`PokeWorkRAM` 是唯一的寫入通道，只接受 `$FC0000–$FCFFFF` 範圍，越界即拒絕並記錄；
見 §5 的金手指段落。

## 4. Bcan 功能對照表

分類：**同等**＝行為與 Bcan 對齊；**改做法**＝目的相同但手段不同；**延後**＝已規劃但
不進第一版；**不做**＝不列入計畫。

### 4.1 檔案

| Bcan 功能 | Go 版做法 | 分類 | 理由 |
|---|---|---|---|
| 開啟 ROM…（Ctrl+O） | 覆蓋選單 →「載入卡帶」進卡帶瀏覽器；桌面沿用 Ctrl+O | 改做法 | 沒有選單列（C3），入口改成覆蓋選單；快捷鍵可以照留 |
| 重新啟動遊戲 | 「重設主機」，並區分冷開機與軟重設 | 改做法 | Bcan 只有一種；本專案的 reset 語意在 `AGENTS.md` 要求「冷開機、soft reset、load state 後都有定義良好的狀態」，介面應反映這個區別 |
| 循環存檔槽（0–9） | 熱鍵「下一個／上一個存檔槽」＋存檔槽畫面直接選 | 同等 | 加上反向循環，十槽用單向循環平均要按五次 |
| 離開 (&X) | 覆蓋選單「離開模擬器」，有未寫回的電池記憶體時先確認 | 改做法 | X11 前端目前 Esc 直接離開，改為 Esc 開選單。行為變更要在發行說明標出 |
| — | 「退出卡帶」回到啟動畫面 | 新增 | Android 沒有命令列可以換卡帶，必須能在不重啟 app 的情況下退出 |
| — | 「主機韌體設定」畫面（IPL／key／兩個音效 BIOS 路徑） | 新增 | Bcan 用 `bios\` 目錄慣例；Android 沒有使用者可及的固定目錄，必須有 UI |

| 冷開機／軟重設分開 | reset 語意在 `AGENTS.md` 有明確區分 |

## 5. 金手指的邊界

C6 允許金手指，但它是 C5 的例外，必須有明確界線，否則「UI 不改寫晶片狀態」這條就
只剩口號。

| 項目 | 規定 |
|---|---|
| 可寫範圍 | 只有 `$FC0000–$FCFFFF`（Work RAM，64 KiB）。越界的 `PokeWorkRAM` 被入口拒絕並記錄，不是被 UI 攔下 |
| 寫入時機 | 只在 frame 邊界，`RunFrame` 之前一次套用全部鎖定項。不在指令中途插入 |
| 讀取時機 | 搜尋快照同樣在 frame 邊界取，兩次快照之間的比較才有定義 |
| 不可觸及 | 晶片暫存器、VRAM、調色盤、sound RAM、SRAM、CPU 暫存器、scheduler 餘數、IRQ 狀態 |
| 存檔互動 | 金手指清單不進 `ACANGOS1` payload。它是外部工具狀態，不是機器狀態 |
| 可觀察性 | 啟用寫入時畫面角落常駐 `CHEAT` 標記；診斷畫面與效能診斷檔都記錄「本次工作階段曾寫入 Work RAM」 |
| 證據效力 | 該工作階段的指令數、framebuffer 雜湊、音訊雜湊一律不得作為硬體證據或回歸基準 |
| 回歸測試 | C10 的九款卡帶回歸在金手指關閉下執行；另加一個測試斷言「金手指關閉時 `PokeWorkRAM` 通道不存在寫入」 |

## 7. 畫面版面

### 7.0 度量與版面設定檔

版面單位是「設計單位」，實際像素 = 設計單位 × `Scale`。`Scale` 由前端計算後傳入，
`ui` 不查詢 DPI。

| 設定檔 | 觸發 | 列高 | 最小命中區 | 面板 padding | 預設字級 |
|---|---|---:|---:|---:|---|
| `compact` | 桌面（鍵鼠／手把） | 24 | 24×24 | 16 | 2× |
| `touch` | Android | 44 | 44×44 | 24 | 3× |

基準網格 8 單位。字身格 8×16 單位（`basicfont` 的 7×13 加 1 單位字距與 3 單位行距）。
字級只有 1×／2×／3× 整數倍，理由：點陣字非整數倍縮放會產生不均勻筆畫。

## 8. 三平台差異化

### 8.1 同一份 `ui` 怎麼吃下三個平台

`ui` 只認兩件事：`Metrics`（表面大小、`Scale`、版面設定檔）與 `Capabilities`。
所有平台差異收斂到這兩者，畫面邏輯只有一份。

| 面向 | 桌面（Linux／macOS） | Android |
|---|---|---|
| 版面設定檔 | `compact` | `touch` |
| 主要輸入 | 鍵盤、滑鼠、手把 | 觸控；可外接手把 |
| 焦點 | 常駐焦點，滑鼠 hover 會移動焦點 | 沒有 hover，焦點只在按下時移動 |
| 返回 | Esc | 系統返回鍵／手勢 |
| 選單入口 | Esc 或長按 Start | 畫面角落的 ☰ 熱區，或雙指輕點 |
| 全螢幕 | 可切換 | 恆為全螢幕，該項隱藏 |
| 檔案選擇 | 內建瀏覽器（列目錄） | 系統 SAF 選擇器取得 URI 後複製進 app 目錄 |
| 文字輸入 | 實體鍵盤 | 內建的自繪鍵盤（見 8.4） |
| 清單捲動 | 滾輪、PageUp／Down | 慣性拖曳、捲軸條加寬到 12 單位 |
| 長按 | 無特別語意 | 等同「次要動作」（相當於右鍵） |

Android 不使用系統輸入法：C3 禁止原生 widget，而金手指與檔名輸入需要的字元集很小
（十六進位、十進位、檔名），自繪鍵盤的成本低於處理 IME 的視窗生命週期。

### 8.2 桌面版面

960×720（3× 整數縮放）為基準。視窗放大時面板不等比放大，而是維持設計單位大小、
面板置中、清單顯示更多列。理由：等比放大會讓 4K 螢幕上的按鈕變成巨物，且點陣字
只能整數倍縮放，中間倍率無處可去。

## 9. 互動模型

### 9.1 抽象事件

前端唯一的責任是把實體輸入翻成這些事件，`ui` 不認識 keysym、`ebiten.Key` 或
Android 的 `KeyEvent`。

```go
// 導覽
Nav{Dir: Up|Down|Left|Right, Repeat bool}
Page{Delta int}                       // ±1 頁
Edge{To: Home|End}

// 動作
Action{Kind: Confirm|Cancel|Menu|Secondary|Delete|TabPrev|TabNext}

// 文字（金手指數值、檔名過濾、版面命名）
Text{R rune}
Edit{Kind: Backspace|Commit|Abort}

// 指標與觸控
Pointer{ID int, X, Y int, Phase: Down|Move|Up|Cancel}
LongPress{ID int, X, Y int}
Wheel{DY int}

// 綁定擷取（只在輸入／熱鍵畫面啟用）
RawKey{Frontend string, Code uint32, Label string}
RawPad{Index int, Button int, Label string}

// 系統
Surface{W, H, Scale int, Profile: Compact|Touch}
Life{Kind: Back|FocusLost|FocusGained|Suspend|Resume}
```

`RawKey`／`RawPad` 是唯一帶平台代碼的事件，只在綁定畫面接受，並且原封不動存進
設定檔（含前端識別字串）。理由：同一個實體鍵在 X11 keysym 與 Ebitengine 的
`ebiten.Key` 底下是不同數值，設定檔必須記得這組綁定是哪個前端寫的，否則跨前端
讀入會得到錯誤的按鍵。

### 9.2 焦點規則

| 規則 | 內容 | 理由 |
|---|---|---|
| 單一焦點 | 每個畫面同時只有一個焦點元件 | 兩個焦點的介面沒有可預測的鍵盤行為 |
| 線性順序 | 元件的焦點順序等於閱讀順序（上到下、左到右） | |
| 群組內環繞 | 清單／格線內部上下環繞 | 十個存檔槽單向不環繞平均多按四次 |
| 跨群組不環繞 | 從清單底部再按下不會跳到上方的分頁列 | 跨區塊環繞會讓使用者失去位置感 |
| 左右調值 | 焦點在「選項」或「滑桿」上時，Left／Right 調整值而非移動焦點 | 值調整比橫向移動常用 |
| 停用項可聚焦 | 停用項顯示為灰階，仍可聚焦；Confirm 時以 toast 說明原因 | 跳過停用項會讓功能看起來不存在，使用者無從得知條件 |
| hover 跟隨 | 桌面：滑鼠移過即移動焦點。觸控：只有 Down 才移動 | 觸控沒有 hover |
| 進入畫面 | 焦點落在第一個可操作項；從子畫面返回時落在來時的那一項 | 返回後焦點歸零會讓連續調整多個項目變得很累 |

### 9.3 返回鍵行為

```
Back / Cancel 事件
   ├─ 有 modal 對話？ ────► 關閉對話（等同「取消」）
   ├─ 在編輯狀態？   ────► 放棄編輯，回到該列
   ├─ 在等待綁定？   ────► 取消綁定擷取，保留原綁定
   ├─ 畫面堆疊 > 1？ ────► 退回上一層
   ├─ 在 S3 覆蓋選單？───► 繼續遊戲（回 S2）
   ├─ 在 S2 執行中？  ───► 開啟覆蓋選單（Android：等同 ☰）
   ├─ 在 S9 停機？    ───► 不動作；停機不能用返回鍵略過
   └─ 在 S0 根畫面？  ───► 確認對話「離開模擬器？」
```

最後一條在 Android 特別重要：直接結束 app 會讓卡帶電池記憶體來不及寫回。有未寫回
資料時，確認對話要說明會遺失什麼。

### 9.4 手把操作選單

| 手把 | UI 事件 |
|---|---|
| D-Pad／左搖桿 | `Nav`（搖桿含 250 ms 首次延遲、80 ms 重複） |
| A（下鍵位） | `Confirm` |
| B（右鍵位） | `Cancel` |
| X | `Secondary`（等同長按／右鍵） |
| Y | `Delete` |
| L／R | `TabPrev`／`TabNext` |
| Start 長按 800 ms | `Menu` |
| Select | 無 |

Start 用長按而不是短按，因為短按 Start 是遊戲輸入；800 ms 長於任何遊戲會用到的
按壓判定。這一條在 `S2` 生效，`S3` 之後 Start 短按即為 `Menu`（此時遊戲沒在跑）。

## 10. 視覺規範

### 10.1 配色

十色語意調色盤，全部以十六進位記錄於 `ui/theme.go`。

| 語意 | 值 | α | 用途 |
|---|---|---:|---|
| `scrim` | `#000000` | 0.55 | 覆蓋選單背後的遊戲畫面；停機畫面用 0.75 |
| `panel` | `#101418` | 0.92 | 面板底 |
| `panel-alt` | `#171C22` | 1.00 | 隔列底色、輸入框 |
| `border` | `#3A4652` | 1.00 | 面板外框、分隔線，1 設計單位 |
| `text` | `#E6EAEE` | 1.00 | 主要文字 |
| `text-dim` | `#94A3AE` | 1.00 | 次要文字、單位、雜湊 |
| `text-off` | `#5A646E` | 1.00 | 停用項 |
| `focus` | `#2B6CB0` | 1.00 | 焦點填色 |
| `focus-text` | `#FFFFFF` | 1.00 | 焦點上的文字 |
| `ok` | `#3F8F5B` | 1.00 | 驗證通過、已載入 |
| `warn` | `#B8862B` | 1.00 | 未驗證、可疑 |
| `error` | `#B4423C` | 1.00 | 拒絕、停機 |

決定與理由：

- **面板不透明度 0.92，不是常見的 0.6。** 遊戲畫面是 256 色高飽和點陣圖，半透明
  面板上的文字對比會被背景的亮塊吃掉。0.92 保留「後面還有畫面」的暗示，但不犧牲
  可讀性。
- **焦點用實心填色，不用外框。** 320×240 放大三倍之後，1 px 外框會被畫成 3 px 的
  粗框，且在 scrim 上不夠顯眼；實心反白在任何縮放下都是一眼可辨。
- **`ok`／`warn`／`error` 的明度刻意分開**（約 L\*47／L\*60／L\*43）。色覺差異者
  靠明度也能區分三者，且三者永遠伴隨文字或符號（✔／⚠／✖），不單獨用顏色承載資訊。
- **不用漸層、不用陰影。** 兩者都需要逐像素運算，在純 CPU 的 X11 前端上每幀重畫
  整個面板的成本不划算，而它們對可讀性沒有貢獻。
- 所有文字對背景的對比比值須 ≥ 4.5:1（`text-off` 對 `panel` 為 ≥ 3:1，停用項本來
  就要弱）；這個檢查寫成單元測試，改色時自動守住。

### 10.2 字級與間距

| 名稱 | 倍率 | 實際大小 | 用途 |
|---|---:|---|---|
| `s` | 1× | 7×13 | 雜湊、位址、次要標註、診斷數值 |
| `m` | 2× | 14×26 | 清單項、按鈕、正文（`compact` 預設） |
| `l` | 3× | 21×39 | 標題、`touch` 版面的正文 |

間距一律取 8 設計單位的倍數：面板 padding 16（`touch` 24）、區塊間距 24、
列內左右 padding 12、圖示與文字間距 8。

### 10.3 狀態表現

| 狀態 | 表現 |
|---|---|
| 一般 | `text` on `panel` |
| 焦點 | 整列填 `focus`，文字 `focus-text`，左緣 4 單位亮條 |
| 按下 | 焦點色明度 −15%，維持 80 ms 後恢復（觸控回饋） |
| 停用 | `text-off`，不填底；右側顯示簡短原因或 `—` |
| 已選（開關） | `[■]` 開／`[ ]` 關，不用打勾符號 |
| 錯誤 | 該列右緣 4 單位 `error` 條，並在底部錯誤列展開說明 |
| 進行中 | 文字後接 8 單位寬的 3 格點動畫（每 400 ms 一格） |

### 10.4 訊息

| 類型 | 位置 | 存活 | 可否抑制 |
|---|---|---|---|
| info toast | 底部置中，離底邊 24 單位 | 2.5 秒 | 可（S5.3 的「抑制操作訊息」） |
| warn toast | 同上 | 4 秒 | 否 |
| 錯誤列 | 目前畫面底部，全寬，`error` 底色 | 直到使用者確認或執行修正動作 | 否 |
| 停機 | 專屬畫面 S9 | 永久 | 否 |

最多同時顯示 3 則 toast，向上堆疊；超過時最舊的立即淡出。錯誤不用 toast，理由已在
4.2 說明：會自己消失的錯誤等於沒說。

## 12. 設定檔

路徑：

| 平台 | 路徑 |
|---|---|
| Linux | `$XDG_CONFIG_HOME/superacan-emu/config.json`，未設時 `~/.config/superacan-emu/` |

```jsonc
    "players": [
      { "keyboard": { "frontend": "x11", "bindings": { "A": 122, "…": 0 } },
        "gamepad":  { "frontend": "x11", "id": "", "bindings": { "A": 0 } } }
    ],
    "hotkeys": { "menu": { "frontend": "x11", "code": 65307 } },

      "layout": "landscape_default", "opacity": 60, "scale": 100,

  },
  "diagnostics": { "layer_mask": 31, "video_registers": false },
  "cheats": { "enabled": false, "lock_all": false }
}
```

相容策略：

| 規則 | 內容 | 理由 |
|---|---|---|
| 未知鍵忽略 | 讀取時不因未知欄位失敗 | 對齊 `Bcan.ini` 的承諾 |
| 未知鍵**保留** | 讀入時把整份 JSON 另存為 `map[string]json.RawMessage`，寫回時把未識別的鍵原樣寫回 | Bcan 只承諾忽略；只忽略不保留的話，舊版模擬器寫一次設定就把新版的欄位刪光 |
| 缺欄位用預設 | 不因缺欄位失敗 | |
| 型別不符 | 該欄位用預設，並記一則 warn，不整份拒絕 | 一個壞欄位不該讓所有設定歸零 |
| 整份無法解析 | 改名為 `config.json.bad`，用預設值繼續 | 見 §11.4 |
| `config_version` | 只在需要語意遷移時提高；提高後舊版讀新檔仍套用「未知鍵忽略」規則 | |
| 原子寫入 | 先寫暫存檔再 `rename` | 沿用 `--save` 的既有做法 |
| 綁定帶前端識別 | 每組綁定記錄寫入它的前端字串 | 見 §9.1 |
| 不存韌體內容 | 只存路徑與雜湊，不存檔案本身 | C8 |

## 13. 分階段交付

順序原則：先解掉會讓後面全部白做的閘門，再做已有底層支援因而立刻可用的功能，
最後才做需要新編碼／新資產的功能。

### P0 閘門（不產生介面）

| 項目 | 產出 | 驗收 |
|---|---|---|
| G1 平台建置矩陣 | [`docs/platform-targets.md`](platform-targets.md) | **已完成。** 五個目標的 `CGO_ENABLED=0` 建置結果與失敗套件路徑都已記錄；`cmd/acan` 在 linux／darwin／android 都失敗，各自原因不同 |
| G2 字型調查 | [`docs/ui-font.md`](ui-font.md) | **已完成。** `basicfont` 只涵蓋可列印 ASCII 與替換字元；`bitmapfont/v4` 的六份來源授權都允許散布，條件是附上授權文字與 Baekmuk 商標標示 |
| G3 拍板 | — | G1 與 G2 是事實蒐集，決策本身仍待使用者拍板：cgo 邊界、字型走嵌入或系統、語言範圍 |

G1 必須先做，因為 Android 若無法在禁 cgo 下建置，整個 §8.3 的設計就沒有承載平台，
而 §8 的觸控設計會影響 §7 每個畫面的度量。G2 必須先做，因為五種語言（不只中文，
法文與西班牙文的重音字元同樣不在 `basicfont` 範圍內）都擋在同一個決策後面。

### P1 `ui` 核心與覆蓋選單

範圍：`ui` 套件骨架、事件與 Intent 型別、`compact`／`touch` 兩套度量、主題、
S3 覆蓋選單、S4 存檔槽、toast 與錯誤列、D1 確認對話。

| 驗收條件 | 方式 |
|---|---|
| `ui` 不 import 任何前端套件 | `go list -deps ./ui` 不含 `ebiten`、`xgb`、`gomobile`；寫成測試 |
| 每個畫面在固定狀態下可重現 | `ui` 測試以 960×720/`compact` 與 1280×720/`touch` 各渲染一次，比對記錄於 `docs/verify-ui.md` 的 SHA-256 |
| 焦點移動可重現 | 對 S3 送出固定事件序列（Down×3、Confirm、Cancel），比對結束狀態的畫面 SHA-256 |
| 存檔槽縮圖來自 payload | 由一份固定的 `ACANGOS1` 檔渲染 S4，比對畫面 SHA-256 |
| 拒絕標示正確 | 準備四種壞檔（損壞、截斷、magic 不符、卡帶不符），S4 各槽的標示與 `docs/save-state.md` 的拒絕理由一致 |
| 兩個前端都能叫出選單並完成存讀檔 | X11 與 Ebitengine 各一次手動 smoke |
| C10 不變 | 九款卡帶 1200-frame 指令數與 framebuffer SHA-256 與 `docs/verify-rom-matrix.md` 相同 |

`touch` 版面在 P1 就要能渲染並雜湊，即使當時還沒有 Android 前端。理由：觸控度量會
逼出「這個面板在 44 單位列高下放不下」這類版面問題，晚發現要重畫每一個畫面。

### P2 啟動、韌體、卡帶瀏覽器

範圍：S0、S0.1、S1、S8。

|---|---|

### P3 輸入、熱鍵、設定檔

範圍：S5、S5.1、S5.2、設定檔讀寫。

| 驗收條件 | 方式 |
|---|---|
| 重新綁定後重啟仍生效 | 寫入設定檔後重讀，綁定相同 |
| 未知鍵保留 | 讀入含未知鍵的設定檔並寫回，未知鍵位元組相同 |
| 損壞設定檔不吞資料 | 餵入壞 JSON，確認產生 `config.json.bad` 且原內容不變 |
| 衝突偵測 | 指定重複熱鍵後，S5.2 的畫面 SHA-256 等於預先記錄的「含衝突標示」版本 |
| 綁定帶前端識別 | X11 寫的設定檔在 Ebitengine 讀入時，不套用不相容的鍵碼並提示重新指定 |

### P4 Android 觸控層

範圍：S5.6、虛擬手把、自繪鍵盤、手勢、返回鍵、方向切換。

前置：G1 通過。

| 驗收條件 | 方式 |
|---|---|
| 橫式與直式版面 | 1280×720 與 720×1280 各渲染一次，比對 SHA-256 |
| 命中區不小於 44 單位 | 測試遍歷所有可操作元件，斷言命中矩形 ≥ 44×44 |
| 命中區大於繪製區 | 同一測試斷言命中矩形每邊比繪製矩形大 ≥ 4 單位 |
| 多點觸控 | 送出五個同時觸點（上＋A＋B＋L＋R），斷言 machine 收到的 pad 位元正確 |
| 返回鍵 | 對 §9.3 的每個分支各送一次 `Back`，斷言結束畫面正確 |
| 選單中虛擬手把隱藏 | S3 開啟時的畫面 SHA-256 不含虛擬手把像素 |

### P5 影像與音訊設定、診斷

範圍：S5.3、S5.4、S7；收尾 `WORKLIST.md` 的「有界、可篩選的除錯介面」。

| 驗收條件 | 方式 |
|---|---|
| 縮放與整數縮放即時生效 | 切換後表面大小改變，`ui` 重新版面，SHA-256 符合記錄值 |
| Scanline 濾鏡正確 | 對固定 framebuffer 套 25/50/75% 後比對三個 SHA-256 |
| 濾鏡不進截圖 | 開啟濾鏡後截圖，PNG 的 SHA-256 等於未開濾鏡時 |
| 圖層遮罩不改變 machine | 切換遮罩前後，68000 指令數相同；`docs/verify-rom-matrix.md` 的基準不變 |
| 診斷數值正確 | 對 Boom Zoo 跑到 frame 1200，S7 顯示的指令數等於 headless 報出的 17,369,003 |
| 音訊設定不回饋核心 | 改音量與緩衝後，同一輸入的音訊樣本序列（未經音量套用前）相同 |

### P6 金手指

範圍：S6.1、S6.2、`ACANCHT1` 讀寫、`BCAN_CHT_1` 匯入。

| 驗收條件 | 方式 |
|---|---|
| 越界拒絕 | 對 `$F40000`、`$FBFFFF`、`$FD0000` 各發一次 `PokeWorkRAM`，三次都被入口拒絕且無寫入 |
| 關閉時無寫入 | 金手指關閉時，一次 1200-frame 執行的 Work RAM 寫入來源不含 UI 通道（以觀察器斷言） |
| 搜尋可重現 | 對固定存檔做「等於 99 → 縮小 → 縮小」，候選位址集合與記錄相同 |
| 上限行為 | 候選超過 4096 時只回 4096 筆並顯示 warn |
| 匯入 Bcan `.cht` | 讀入一份 `BCAN_CHT_1` 檔，項目數與內容與來源相同 |
| 標記可見 | 啟用寫入時 S2 的畫面 SHA-256 等於預先記錄的「含 CHEAT 標記」版本 |

### P7 擷取

範圍：S3 的截圖項、GIF 擷取、`--capture-sink` 外部程序。

| 驗收條件 | 方式 |
|---|---|
| 截圖等同硬體輸出 | 截圖 PNG 解碼後的像素與 `--screenshot` 產出的位元組相同 |
| GIF 幀數與時距 | 錄 120 個 machine frame，GIF 有 60 幀、每幀 delay=3 |
| GIF 用硬體調色盤 | GIF 的 global palette 等於該幀的 UM6618 調色盤展開值，無量化 |
| 外部 sink | `--capture-sink "cat > out.raw"` 產生的位元組數 = 幀數 × 320 × 240 × 4 |
| 擷取不影響時序 | 開啟擷取跑 1200 frame，指令數與 framebuffer SHA-256 不變 |

### P8 多語言

前置：G2 通過。

| 驗收條件 | 方式 |
|---|---|
| 字型授權已確認可散布 | `docs/ui-font.md` 記錄授權全文出處與判定 |
| 五種語言的字串表完整 | 測試斷言每個 key 在五種語言都有值，且沒有多餘 key |
| 切換不需重啟 | 切換語言後同一畫面的 SHA-256 等於該語言的記錄值 |
| 版面不溢出 | 對每個畫面在五種語言下渲染，斷言沒有文字超出其容器矩形 |

### 為什麼是這個順序

| 位置 | 理由 |
|---|---|
| P0 最前 | Android 建置與字型是兩個會讓後續工作報廢的閘門，不是細節 |
| P1 第二 | 存讀檔已完成（`docs/save-state.md`），覆蓋選單能立刻取代寫死的 F5／F7，投入產出比最高；同時把 `ui` 的邊界測試建起來，之後每一階段都靠它 |
| P2 第三 | Android 沒有命令列，「能不指定路徑就開起來」是它能被使用的前提 |
| P3 第四 | 觸控層要重用綁定與設定檔的資料結構，順序反過來會做兩次 |
| P4 第五 | 前四階段把 `ui` 的元件備齊之後，觸控層才是換度量與加手勢，不是重寫 |
| P5 第六 | 診斷面板是既有 CLI 能力的搬移，不新增能力，可以晚做 |
| P6 第七 | 金手指是 C5 的例外，晚做可以讓「UI 不寫 machine」這個結構先被測試固定下來 |
| P7 第八 | 擷取需要新編碼路徑，且與畫面正確性的收斂無關 |
| P8 最後 | 依賴 G2，且字串表在功能定案前會反覆改 |

每一階段都要維持 C10：九款卡帶的 1200-frame 指令數與 framebuffer SHA-256 不變。
這些數字一動就表示 UI 滲進了模擬路徑。

## 14. 不做的項目

| 項目 | 理由 |
|---|---|
| Windows 發行 | C1。既有的 `windows/amd64` 建置只留作 CI 的禁 cgo 檢查 |
| 瀏覽器（`js/wasm`）發行 | C1。同上 |
| MP4／H.264／AAC 錄影 | 純 Go 沒有可用的編碼器；要做等於承諾自行實作視訊編碼器 |
| 系統原生選單列、對話框、檔案選擇器（Android SAF 除外） | C3。Android 的 SAF 是取得檔案存取權的唯一途徑，屬平台權限而非介面繪製 |
| GPU 著色器濾鏡（第一版） | 畫面正確性尚未收斂，濾鏡會讓像素對帳更難判讀；且 X11 前端沒有 GPU 路徑，會造成平台間的畫面差異 |
| 倒帶（rewind） | 需要環形 save state 緩衝，而 save state 在所有裝置事件邊界的決定性仍列於 `CONTEXT.md` 的未證實項 |
| 任意位址的記憶體編輯器 | C6 只開放 Work RAM。寫 VRAM 或裝置暫存器等於用 UI 偽造硬體狀態 |
| 反組譯視窗、中斷點、單步除錯 | 有價值但屬除錯器而非介面；先把有界 trace 搬進診斷畫面，之後另案評估 |
| 網路對戰 | 需要決定性 rollback 與輸入延遲模型，與目前的驗證目標無關 |
| 成就、遊戲資料庫、線上封面圖 | 需要外部服務與網路，且 C8 禁止散布遊戲畫面 |
| 卡帶封面預覽 | C8 |
| 音訊等化器與各聲道增益 | UM6619 的混音增益與削波仍是未定事實，提供調整介面等於邀請使用者用聽感覆蓋硬體行為 |
| 佈景主題／使用者換色 | 一組經過對比檢查的配色比十組沒檢查過的有用；有明確需求再談 |

## 15. 決策紀錄

2026-09-01 拍板四項，兩項因為新事實重開，兩項仍待決。

### 已決定

| 編號 | 決策 | 結果 | 依據與後果 |
|---|---|---|---|
| D2 | 字型：嵌入或讀系統 | **嵌入 `bitmapfont/v4`** | 六份來源授權（Baekmuk、OFL-1.1 ×3、Public Domain、M+ Bitmap）都允許隨軟體散布；代價是 2.5 MB 資料，發行包要附授權文字與 Baekmuk 商標標示。見 [`docs/ui-font.md`](ui-font.md) |
| D3 | 法文與西班牙文是否要做 | **要做** | `basicfont.Face7x13.Ranges` 實測只有 `U+0020`–`U+007F` 與替換字元，這兩種語言與中文擋在同一個閘門；D2 一嵌入就一起解決。五種語言全做 |
| D4 | 金手指是否進第一個發行版 | **進，但加約束** | 啟用時畫面常駐標記，該工作階段的 frame／audio 雜湊不得作硬體證據。P6 的驗收條件要包含這兩點 |
| D6 | macOS 前端走哪條路 | **purego** | `oto/v3` 在 darwin 兩個架構的 `CGO_ENABLED=0` 建置都成功；Ebitengine 的 `internal/cocoa` 與 Metal 驅動也已是純 Go。缺的只剩視窗與輸入層，見 [`docs/platform-targets.md`](platform-targets.md) |

### 因新事實重開

| 編號 | 決策 | 新事實 | 待決的選項 |
|---|---|---|---|
| D1 | Android 在禁 cgo 下怎麼辦 | 原本寫成「工作量遠超過介面工作總和」，實測後不是工作量問題而是**沒有路**：`-buildmode=c-shared requires external (cgo) linking`，而 Android 應用的原生碼一定要是共享程式庫。同一份程式建成**執行檔**則成功——核心跑得動，不能成立的是應用程式形式 | (1) Android 對 cgo 開例外 (2) Android 退出發行範圍 (3) Go 跑核心、Java 寫介面的雙行程架構。三者代價見 [`docs/platform-targets.md`](platform-targets.md) |
| D5 | 擷取做到哪一級 | 決定是「做完整錄影」。純 Go 有容器（`abema/go-mp4`）與 MJPEG（`image/jpeg`），沒有 H.264 與 AAC 編碼器；唯一避開 cgo 的 H.264 是 `y9o/go-openh264`，用 purego 在執行期載入 Cisco 的 OpenH264 | 甲：MP4／MJPEG＋PCM，純 Go 無執行期相依 乙：MP4／H.264，需執行期原生函式庫與 Cisco 授權處理 丙：甲為預設、乙為選配。見 [`docs/capture-formats.md`](capture-formats.md) |
